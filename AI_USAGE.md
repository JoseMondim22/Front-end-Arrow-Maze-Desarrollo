### ScoringStrategy y dos politicas de puntuacion

- **Herramienta de IA utilizada:** Claude Code  (Modelo Claude Sonnet 5)
- **Prompt o instruccion proporcionada:** Crear dos ScoringStrategy: una que inicia en el puntaje maximo y disminuye por tiempo y movimientos fallidos, y otra que solo disminuye por movimientos fallidos.
- **Resultado obtenido:** Se creo la interfaz ScoringStrategy y el tipo ScoringInput en shared/services/, mas dos implementaciones: TimeAndFailedMovesScoringStrategy (penaliza tiempo + movimientos fallidos) y FailedMovesScoringStrategy (solo movimientos fallidos). Las penalizaciones son proporcionales a los presupuestos del nivel (fraccion del timeLimit y de maxMoves), con pesos inyectados por constructor (OCP) y el puntaje siempre clampeado a [0, maxPossibleScore]. Typecheck en strict paso sin errores.
 
- **Lecciones aprendidas o limitaciones identificadas:** Se aclaro que movimiento fallido no es lo mismo que movimiento usado: un movimiento saca una cadena (progreso) o revierte (error), y solo los reverts deben penalizar. Por eso se extendio el input de scoring del 6.5 con failedMoves. Consecuencia pendiente: GameSession debe llevar un contador de failedMoves (sumar cuando slideChain devuelve Reverted) para poder alimentar estas estrategias al cablear el scoring. Los pesos exactos siguen pendientes (17.1); quedaron configurables para tunearlos sin tocar codigo.

### Fix: condicion de carrera entre efectos de GameScreen (Victory fantasma al entrar a un nivel)

- **Herramienta de IA utilizada:** Claude Code (Modelo Claude Sonnet 5)
- **Prompt o instruccion proporcionada:** El usuario reporto que, tras jugar y ganar un nivel, volver a tocar cualquier nivel desde LevelSelect abria directo la pantalla de Victory en vez del tablero. Un intento anterior (limpiar session a null al inicio de useGameStore.startGame) no habia resuelto el problema por completo.
- **Resultado obtenido:** Se identifico que GameScreen.tsx tiene 3 useEffect declarados en orden: (1) llama a startGame(level), (2) arranca el intervalo de tick, (3) redirige a Victory/Defeat si session esta en estado terminal. En el primer render de un montaje nuevo, los 3 efectos corren en el mismo commit contra el MISMO session capturado en ese render (el de la partida anterior, ya en Victory). El set({session: null, ...}) que hace el efecto 1 dentro de startGame solo agenda un re-render en React/Zustand, no lo produce sincronicamente antes de que corra el efecto 3 — asi que el efecto 3 seguia viendo la session vieja en Victory y redirigia de inmediato, antes de que la partida nueva terminara de cargar. Se agrego un ref hasLoadedRef que arranca en false en cada cambio de level, se resetea a false al iniciar el efecto de startGame, y se pone en true recien cuando la promesa de startGame(level) resuelve; el efecto de redireccion a Victory/Defeat ahora chequea ese ref antes de mirar session, por lo que ignora el session viejo heredado del montaje anterior. Typecheck sin errores; se reinicio Metro con cache limpia para verificar en el emulador.
 
- **Lecciones aprendidas o limitaciones identificadas:** El fix anterior (limpiar session dentro de startGame) atacaba el sintoma equivocado: asumia que el problema era que session quedaba stale ENTRE renders, cuando en realidad el bug ocurria DENTRO del mismo commit inicial, por como React ejecuta multiples useEffect de un mismo render en orden pero todos leyendo el mismo closure de props/state de ESE render — un set() disparado por el primer efecto no es visible para el tercer efecto del mismo commit. La leccion general: cuando dos efectos de un componente coordinan estado compartido con un store externo (Zustand), no alcanza con "limpiar el estado antes" si el efecto que lee ese estado corre en el mismo flush; hace falta un mecanismo explicito (ref, no state) que marque "todavia no termino de cargar" para el mismo ciclo de vida del montaje.
